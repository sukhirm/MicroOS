## 1. Executive Summary

This document presents a comprehensive technical audit of the current Micro-OS UEFI boot architecture and defines an implementation plan for producing a **genuine, standards-compliant UEFI-bootable ISO image (`.iso`)**.

The target goal is to enable **Live OS demonstration on physical HP Victus hardware directly from a USB drive**, without installing any bootloader, files, or data onto the internal Samsung NVMe SSD.

### Key Audit Conclusions
1. **Current Image Format:** The existing build system (`runner`) generates a raw **GPT/FAT16 disk block image (`target/micro_os_uefi_release.img`, 3.06 MiB)**. This image is directly flashable to a USB drive via block-writing utilities (Rufus in "DD Image mode" or Balena Etcher), but it is **not an ISO 9660 optical image**.
2. **Bootloader Capabilities:** The official `bootloader` crate (v0.11.17) generates the complete, bootable FAT filesystem image containing `\EFI\BOOT\BOOTX64.EFI` (167 KiB) and `kernel-x86_64` (971 KiB), but does not provide an ISO 9660 / El Torito packaging pipeline.
3. **Tool Availability:** Standard external Linux ISO creation utilities (`xorriso`, `mkisofs`) are not natively present on Windows, and Microsoft `oscdimg` is not installed on the development host.
4. **Recommended Architecture:** A native Rust packaging engine within `runner/src/iso.rs` that takes the proven FAT EFI System Partition generated by `bootloader::DiskImageBuilder`, wraps it in an **ISO 9660 filesystem with an El Torito Boot Catalog containing a UEFI Platform ID (`0xEF`) Section Entry**, and injects an **MBR partition table (Type `0xEF`) in Sector 0**. This creates a **Hybrid UEFI Bootable ISO** supported by both optical drives and USB flash media.
5. **Safety Constraints:** In strict adherence to project instructions, no host disks, internal partitions, or BIOS settings will be touched; both `.img` and `.iso` artifacts will remain reproducible and well below the 500 MB teacher limit (~3.1 MiB).

## 2. Task 1: Inspection of Current Boot Structure

### 2.1 Kernel Bootloader Configuration
In [kernel/src/main.rs](file:///C:/Users/sukhi/OneDrive/Documents/MicroOS_New/kernel/src/main.rs#L27-L36):
```rust
pub static BOOTLOADER_CONFIG: BootloaderConfig = {
    let mut config = BootloaderConfig::new_default();
    config.mappings.physical_memory = Some(Mapping::Dynamic);
    config.kernel_stack_size = 128 * 1024;
    config
};

entry_point!(kernel_main, config = &BOOTLOADER_CONFIG);
```
- The kernel uses the official `bootloader_api` crate (v0.11.17).
- It requests dynamic physical memory mapping, a 128 KiB stack, and accepts `&'static mut BootInfo`.

### 2.2 Runner Disk Image Generation
In [runner/src/main.rs](file:///C:/Users/sukhi/OneDrive/Documents/MicroOS_New/runner/src/main.rs#L58-L64):
```rust
let uefi_boot = bootloader::UefiBoot::new(&kernel_bin_path);
uefi_boot.create_disk_image(&uefi_img_path)?;
```
Under the hood in `bootloader-0.11.17/src/lib.rs`:
1. `DiskImageBuilder::create_uefi_fat_partition()` writes an in-memory FAT16 filesystem into a temporary file.
2. It inserts `efi/boot/bootx64.efi` (the embedded 64-bit UEFI bootloader binary) and `kernel-x86_64` (the compiled Micro-OS ELF kernel).
3. `gpt::create_gpt_disk()` creates a GUID Partition Table disk layout wrapping this FAT partition.
4. The output is written to `target/micro_os_uefi_release.img`.

### 2.3 Physical Structure of `target/micro_os_uefi_release.img`
Our low-level binary inspection of the generated image revealed:
- **Total Image Size:** 3,211,264 bytes (6,272 sectors of 512 bytes = 3.06 MiB).
- **LBA 0 (Offset 0): Protective MBR**
  - MBR Signature: `0xAA55` at bytes 510–511.
  - Partition 1: Type `0xEE` (Protective GPT), starting at LBA 1, spanning 6,271 sectors.
- **LBA 1 (Offset 512): Primary GPT Header**
  - Signature: `b"EFI PART"`.
  - First usable LBA: 34; Last usable LBA: 6,238; Partition entries at LBA 2.
- **LBA 2–33 (Offset 1,024): GPT Partition Entries**
  - Partition 1: Name = `'boot'`, Type GUID = `C12A7328-F81F-11D2-BA4B-00A0C93EC93B` (EFI System Partition).
  - Start LBA: 34; End LBA: 6,177 (6,144 sectors = exactly 3,145,728 bytes / 3.00 MiB).
- **LBA 34 (Offset 17,408): FAT16 EFI System Partition**
  - OEM Identifier: `'MSWIN4.1'`, Bytes per Sector: 512, Sectors per Cluster: 4 (2,048-byte clusters).
  - Reserved Sectors: 1, Number of FATs: 2, FAT Size: 5 sectors.
  - Root Directory: Starts at byte offset 5,632 from partition start (512 directory entries).
- **Files Stored Inside the Partition:**
  1. `\EFI\BOOT\BOOTX64.EFI`: 167,424 bytes (Cluster 4).
  2. `\KERNEL-X86_64`: 971,256 bytes (Cluster 86).
  3. `\BOOT.JSON`: Bootloader configuration.

### 2.4 How the Kernel is Loaded
1. **UEFI Firmware Hand-off:** On boot, the physical laptop firmware queries NVRAM or default paths, loading `\EFI\BOOT\BOOTX64.EFI`.
2. **Framebuffer Initialization:** `BOOTX64.EFI` invokes UEFI GOP (Graphics Output Protocol) to query native display modes and initialize the linear framebuffer (e.g. 1920x1080 32-bit RGB/BGR).
3. **Memory & ELF Loading:** The bootloader allocates physical pages, loads the ELF segments of `kernel-x86_64`, constructs 4-level page tables with physical memory dynamically mapped, and allocates a 128 KiB stack.
4. **Boot Services Termination:** The bootloader retrieves the final UEFI memory map, calls `ExitBootServices()`, constructs `BootInfo`, and jumps to `kernel_main`.

### 2.5 Bootloader ISO 9660 & El Torito Support
- The `bootloader` crate (v0.11.17) **does not include an ISO 9660 generator**. Its image builder only outputs GPT hard disk images (`.img`).
- **Crucial Finding:** The embedded UEFI executable (`BOOTX64.EFI`) **does not care whether the underlying physical medium is a hard drive, USB flash drive, or CD/DVD**. When booting an El Torito ISO, the UEFI firmware reads the El Torito catalog, mounts the embedded FAT ESP image as a standard UEFI block device, and launches `BOOTX64.EFI` from it. Once launched, `BOOTX64.EFI` uses standard UEFI file protocols on the mounted FAT volume.

## 3. Task 2: Tool Evaluation & Selection

### 3.1 Evaluation of Standard Tools on Windows
We performed an audit of candidate ISO creation tools in the Windows host environment:

| Candidate Tool | Availability on Host | Compatibility & Assessment | Recommendation |
| :--- | :---: | :--- | :--- |
| **`xorriso`** | **Not Installed** | GNU/Linux utility (libisoburn). Not available via `winget`. Requires installing Cygwin/MSYS2, which introduces external non-native toolchains and breaks reproducible builds. | **Rejected** (Unportable) |
| **`mkisofs` / `cdrtools`** | **Not Installed** | Deprecated Windows ports exist from the 1990s/2000s, but they are unmaintained, do not cleanly support modern El Torito Platform ID `0xEF`, and are not packaged in winget. | **Rejected** (Obsolescence) |
| **`oscdimg` (Windows ADK)** | **Not Installed** | Official Microsoft tool capable of El Torito EFI booting (`-b` flag). However, it is not present on the machine and requires a multi-gigabyte Windows ADK installation. | **Rejected** (Heavy dependency) |
| **`7-Zip`** | **Available in Winget** | Capable of reading/extracting ISOs, but **cannot author El Torito bootable ISOs** (does not write boot catalog records). | **Rejected** (Extraction only) |

### 3.2 Recommended Solution: Native Rust ISO Synthesizer in `runner`
Rather than introducing external third-party dependencies, we will implement a clean, lightweight ISO 9660 + El Torito engine directly in `runner/src/iso.rs`.

**Why this is the superior approach:**
1. **100% Dependency-Free:** Compiles natively with `cargo build -p runner` on any host (Windows, Linux, macOS).
2. **Reuses the Proven FAT Partition:** We do not write a FAT filesystem from scratch. We invoke `bootloader::DiskImageBuilder::create_uefi_fat_partition()`, which already produces the exact, verified FAT16 image containing `BOOTX64.EFI` and `kernel-x86_64`.
3. **Pure ISO 9660 + El Torito Specification Compliance:** The ISO format for UEFI boot is deterministic, well-documented, and mathematically straightforward (detailed below).
4. **Hybrid MBR Injection:** By adding a standard MBR partition entry (Type `0xEF`) in Sector 0, the resulting `.iso` becomes a **Hybrid ISO**—it can be burned directly to optical media OR written as a raw disk image to a USB flash drive.

## 4. Task 3: Proposed Hybrid ISO 9660 Boot Architecture

### 4.1 Sector Layout (Logical Sector Size = 2,048 Bytes)

```
Byte Offset      Sector LBA   Content Description
----------------------------------------------------------------------------------------------------
0x00000 - 0x007FF   LBA 0     System Area: Sector 0 contains Hybrid MBR Partition Table
                              - Partition 1: Type 0xEF (EFI System Partition) pointing to Sector 20
0x00800 - 0x07FFF   LBA 1-15  System Area: Reserved / padding (zeros)
0x08000 - 0x087FF   LBA 16    ISO 9660 Primary Volume Descriptor (PVD)
                              - Type: 0x01, Identifier: "CD001", Version: 0x01
                              - Volume ID: "MICRO_OS_LIVE", Block Size: 2048
0x08800 - 0x08FFF   LBA 17    El Torito Boot Record Volume Descriptor
                              - Type: 0x00, Identifier: "CD001", Version: 0x01
                              - Boot System Identifier: "EL TORITO SPECIFICATION"
                              - Pointer to Boot Catalog: LBA 19 (Offset 0x47, 4 bytes LE)
0x09000 - 0x097FF   LBA 18    Volume Descriptor Set Terminator
                              - Type: 0xFF, Identifier: "CD001", Version: 0x01
0x09800 - 0x09FFF   LBA 19    El Torito Boot Catalog (2,048 bytes)
                              - 1. Validation Entry (32 bytes, Header 0x01, Key 0x55AA, Checksum)
                              - 2. Default Initial Entry (32 bytes, non-bootable legacy fallback)
                              - 3. Section Header (32 bytes, Header 0x91, Platform ID 0xEF = UEFI)
                              - 4. Section Entry (32 bytes, Bootable 0x88, Load RBA = LBA 20)
0x0A000 - End       LBA 20+   Embedded FAT16 EFI System Partition (3.00 MiB)
                              - Sourced directly from bootloader::DiskImageBuilder
                              - Contains: \EFI\BOOT\BOOTX64.EFI, \KERNEL-X86_64, \BOOT.JSON
```

### 4.2 El Torito Boot Catalog Binary Specification (LBA 19)

#### 1. Validation Entry (Bytes 0–31):
- `Offset 0x00 (1B):` Header ID = `0x01`
- `Offset 0x01 (1B):` Platform ID = `0x00` (x86)
- `Offset 0x02 (2B):` Reserved = `0x0000`
- `Offset 0x04 (24B):` Manufacturer ID = `"MicroOS UEFI Bootloader"` (space-padded ASCII)
- `Offset 0x1C (2B):` **Checksum Word**: Calculated such that the sum of all sixteen 16-bit little-endian words in the 32-byte entry equals `0x0000`.
- `Offset 0x1E (2B):` Signature = `0x55, 0xAA`

#### 2. Default Initial Entry (Bytes 32–63):
- `Offset 0x00 (1B):` Boot Indicator = `0x00` (Not bootable in legacy BIOS mode)
- `Offset 0x01 (1B):` Media Type = `0x00` (No emulation)
- `Offset 0x02 (2B):` Load Segment = `0x0000`
- `Offset 0x04 (1B):` System Type = `0x00`
- `Offset 0x06 (2B):` Sector Count = `0x0001`
- `Offset 0x08 (4B):` Load RBA = `0x00000000`

#### 3. Section Header Entry — UEFI Platform (Bytes 64–95):
- `Offset 0x00 (1B):` Header Indicator = `0x91` (Final section header)
- `Offset 0x01 (1B):` **Platform ID = `0xEF` (Unified Extensible Firmware Interface / UEFI)**
- `Offset 0x02 (2B):` Number of section entries = `0x0001`
- `Offset 0x04 (28B):` Section Identifier = `"UEFI Boot Image"` (space-padded)

#### 4. Section Entry — UEFI Boot Image (Bytes 96–127):
- `Offset 0x00 (1B):` Boot Indicator = `0x88` (Bootable)
- `Offset 0x01 (1B):` Media Type = `0x00` (No emulation)
- `Offset 0x02 (2B):` Load Segment = `0x0000` (Standard UEFI)
- `Offset 0x04 (1B):` System Type = `0x00`
- `Offset 0x06 (2B):` Sector Count = Number of 512-byte sectors in the FAT image (`(fat_size + 511) / 512`)
- `Offset 0x08 (4B):` **Load RBA = LBA 20** (`0x00000014`, byte offset `0x0A000`): Points directly to the start of the embedded FAT ESP image.

### 4.3 Hybrid USB Bootability (Sector 0 MBR)
When writing an ISO to a USB drive with raw block tools (or if UEFI BIOS reads a USB as a mass storage device rather than CD-ROM), the firmware checks the MBR at LBA 0:
- Sector 0 (512 bytes):
  - Bytes 0–445: Bootstrap code / zeros.
  - Bytes 446–461: **Partition Entry 1**:
    - Bootable flag: `0x80`
    - Partition Type: **`0xEF` (EFI System Partition)**
    - Starting LBA: $20 \times 4 = 80$ (in 512-byte disk sectors; corresponds to ISO Sector 20)
    - Sector Count: Number of 512-byte sectors in the FAT image ($6,144$ sectors = 3.00 MiB)
  - Bytes 510–511: MBR signature `0x55, 0xAA`.
- This ensures **dual compatibility**: optical drives/virtual mounts read El Torito at Sector 17/19, while USB drives read Partition 1 at Sector 0.

## 5. Task 4: Verification & Validation Protocol

In strict compliance with requirements, validation will not rely on QEMU or VMware, nor write to physical USB drives. Instead, an automated host verification suite will inspect the generated ISO image:

### Automated Validation Suite (`runner/src/iso_verify.rs` or `runner/tests/`):
1. **ISO 9660 PVD Verification:**
   - Byte offset `0x8000` must be `0x01`.
   - Byte offset `0x8001..0x8006` must equal `b"CD001"`.
   - Logical block size at `0x8080` must equal 2048 (both-endian).
2. **El Torito Boot Record Verification:**
   - Byte offset `0x8800` must be `0x00`.
   - Byte offset `0x8801..0x8806` must equal `b"CD001"`.
   - Boot system ID at `0x8807` must start with `b"EL TORITO SPECIFICATION"`.
   - Pointer at `0x8847` must equal LBA 19 (`0x00000013`).
3. **Descriptor Set Terminator Verification:**
   - Byte offset `0x9000` must be `0xFF` (`b"CD001"`).
4. **Boot Catalog Verification (Offset `0x9800` / LBA 19):**
   - Validation Entry Header ID must be `0x01`.
   - Validation Entry Key bytes at offset `0x981E` must be `0x55, 0xAA`.
   - 16-bit word-sum of the 32-byte Validation Entry must equal `0x0000`.
   - Section Header at offset `0x9840` must have Header `0x91` and **Platform ID `0xEF` (UEFI)**.
   - Section Entry at offset `0x9860` must have Bootable flag `0x88` and Load RBA = 20 (`0x00000014`).
5. **Embedded FAT ESP Image Verification (Offset `0x0A000` / LBA 20):**
   - Must contain a valid FAT boot sector with signature `0xAA55`.
   - Root directory traversal must find `EFI/BOOT/BOOTX64.EFI` (> 100 KiB) and `KERNEL-X86_64` (> 500 KiB).
6. **Hybrid MBR Verification (Offset 0x0000 / LBA 0):**
   - Byte 510–511 must be `0xAA55`.
   - Partition 1 type must equal `0xEF`, starting at LBA 80 (512-byte blocks).
7. **Size & Limit Verification:**
   - Total ISO size must be ~3.1 MiB (verified << 500 MB limit).
8. **Integrity of Existing Image:**
   - `target/micro_os_uefi_release.img` must remain byte-for-byte intact and buildable.
